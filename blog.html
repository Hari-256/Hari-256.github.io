Five Years at Nokia: Lessons from Building Secure Java Frameworks

I went from a five-year integrated MTech at VIT to building the core Java framework and access-control layers that teams across Nokia depend on. This is that journey, and what I learned along the way.

The starting line#

I'm Hari Krishna Kothapalli, a Software Engineer based in Bangalore. My path into software started at VIT, Vellore, where I completed a five-year integrated MTech in Software Engineering (2016–2021) with a CGPA of 8.48. Those years gave me more than a degree. They taught me to treat software as engineering: object-oriented design, data structures and algorithms, and the discipline of building things that last.

In August 2021, I joined Nokia as a Software Engineer, and I've been there ever since.

Building the foundation other teams stand on#

Most of my work lives inside Nokia's core internal Java framework, the shared layer that multiple product lines are built on. Framework work is a different kind of engineering. Your users are other engineers, and every design decision ripples outward into products you may never touch directly.

That changes how you write code. I focus heavily on modularity and reusability. Components should be easy to adopt, hard to misuse and stable across releases. A well-designed framework API helps product teams move faster. A poorly designed one costs everyone.

A framework is a product whose customers are engineers. Treat its APIs like promises.

Security is a feature, not an afterthought#

A big part of my role is Identity & Access Management. I design and enforce fine-grained IAM protocols and Role-Based Access Control (RBAC) matrices across core internal applications. The goal is that every user and service gets exactly the access it needs, and nothing more.

I've also spent a lot of time in the less glamorous corners of security: authentication flows, session handling and redirection logic. Some issues look like small redirect bugs on the surface but turn out to sit right on a trust boundary. Working through them taught me to think in terms of least privilege, Privileged Access Management (PAM) and Zero Trust: never assume a request is safe just because of where it came from.

Making it fast, and keeping it stable#

The framework powers high-volume internal systems, so performance matters. I develop and optimize critical business logic using advanced Java features like multithreading. Concurrency is powerful but unforgiving. Shared state, race conditions and thread-safety issues don't always show up in testing. My rule of thumb is to measure first, keep shared state minimal, and make the concurrency model obvious to the next person who reads the code.

Root cause over quick fixes#

When something breaks in a core framework, it rarely breaks in only one place. I chase complex defects down to the root cause instead of patching the symptom, and I ship fixes fast enough to prevent outages downstream. A good root-cause analysis doesn't just close a ticket. It prevents the next three.

Engineering is a team sport#

Some of the most valuable work I do isn't code at all:

  • Collaboration: I partner with product teams across different Nokia verticals to understand their requirements and integrate framework capabilities into their applications.
  • Code reviews: I review new features and enhancements for coding standards, performance and security. Quality gets built in reviews, and they're also where I learn the most.
  • Documentation: I write technical documentation and best-practice guides so new engineers can onboard smoothly and knowledge doesn't live in one person's head.
  • Delivery: I work in an Agile setup with Git, GitHub, Jenkins and GitLab CI pipelines, managing complex branches and keeping integration smooth.

My toolbox#

Day to day, I work with Core Java (JDK 8+), Spring Boot, REST APIs and MySQL. I deploy with Docker, Kubernetes and AWS across Windows, Linux and RHEL servers. For automation I use Python, Selenium and AutoIt, and I test with JUnit.

More recently, AI tools like Claude, GitHub Copilot and Cursor have become part of how I work. I use them to explore unfamiliar code, draft tests and speed up routine tasks. In fact, I built this website with help from an AI agent in Cursor. The design, the judgment and the responsibility for what ships still belong to the engineer, but the feedback loop is much faster.

Recognition#

I'm grateful to have received two awards at Nokia:

  • Excellent Support & Development Award (verify)
  • Dedicated and Emerging Employee Award (verify)

To me, they're a reminder that dependable support and consistent delivery matter as much as clever code.

Five lessons from five years#

  1. Design APIs as if you'll have to support them forever. In a framework, you will.
  2. Security belongs in the design review, not the post-mortem.
  3. Measure before you optimize, especially with concurrency.
  4. Fix the root cause, then write down what you learned.
  5. Clear documentation and thoughtful code reviews extend your impact beyond your own keyboard.

What's next#

I want to go deeper into cloud-native architecture and identity security, where scalable systems and trustworthy access meet. If you're working on similar problems, or just want to talk Java, IAM or DevOps, I'd love to connect on LinkedIn or by email.
